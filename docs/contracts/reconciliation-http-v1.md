# Reconciliación y API de obligaciones V06

Todas las rutas usan `/api/v1`, responden `X-CrashMemory-Contract: 2026-09-20.v1` y `Cache-Control: no-store`. La cookie de sesión pertenece a CrashMemory. Las mutaciones exigen `Origin` igual a `APP_ORIGIN` cuando se envía, `Content-Type: application/json` y `X-CSRF-Token` devuelto en el login. No hay registro público. Error uniforme: `{ "error": { "code", "message", "requestId" } }`. Un ID UUID mal formado da 400; un ID de otro usuario da 404; `expectedVersion` obsoleta da 409.

| Método | Ruta                                      | Respuesta / cuerpo                                                                                                                                                                                                                                                                                                                                                                                              |
| ------ | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| GET    | `/obligations/:id`                        | `{data:{id,state,currentVersionId,createdAt,updatedAt,versions,protectedFields,conflicts}}`. Versiones en orden descendente, cada una con evidencia `id,kind,sourceItemRevisionId,attachmentId,page,startOffset,endOffset,quote,contentSha256,url`. `protectedFields` muestra último valor confirmado/corregido por campo y versión de origen. Conflictos muestran propuesta, razón, estado y IDs de evidencia. |

Las mutaciones exitosas responden `{data:{id,state,currentVersionId,revision}}` de la misma transacción. `Money` es `{amount:"48.50",currency:"COP"}`, siempre cadena decimal exacta; `due` conserva `{kind:"civil_date",date:"2026-10-15",timeZone:"America/Bogota"}` o el instante con zona. La cita `email_body_fragment` usa offsets UTF-16 del cuerpo; `pdf_text_fragment` usa offsets UTF-16 de la página uno-indexada. La web puede comprobar `text.slice(startOffset,endOffset) === quote` y SHA-256 del texto completo.

## Identidad y estados

Sólo se deduplican candidatos cuando emisor y número de factura/recibo/liquidación están juntos en un fragmento verificado, con etiqueta y límites de token exactos. El hash es por usuario. Un número de cuenta o cliente, título, importe y fecha no identifican una factura. Candidatos sin ancla fiable crean entidades `candidate` separadas; replay del mismo candidato usa su vínculo durable. La hora `observed_at` de la revisión ordena propuestas del mismo ancla: una más antigua se guarda como conflicto `out_of_order`, sin alterar versión ni recordatorio vigente. La igualdad de importes ignora ceros decimales insignificantes.

| Estado actual                    | Acción manual         | Estado resultante                                                 |
| -------------------------------- | --------------------- | ----------------------------------------------------------------- |
| candidate                        | confirm               | confirmed; protege todos los campos                               |
| candidate / confirmed            | correct               | mismo estado; protege campos editados                             |
| candidate / confirmed / conflict | discard               | discarded                                                         |
| confirmed                        | pay                   | paid                                                              |
| conflict                         | resolve accept/reject | estado previo candidate o confirmed al cerrar el último conflicto |
| paid / discarded                 | propuesta inferida    | permanece terminal; propuesta visible como `terminal_state`       |

Una inferencia nueva sólo modifica automáticamente los campos no protegidos de `candidate` y crea una versión inmutable. Si contradice una corrección/confirmación, la versión actual conserva sus valores y el estado pasa a `conflict`; la propuesta y su evidencia quedan en `conflicts`. Mientras haya conflictos abiertos no se aplican otras inferencias. Resolver exige versión vigente. Rechazar un conflicto de un candidato corregido vuelve a `candidate`, sin confirmarlo. Los conflictos `out_of_order` aparecen incluso si el estado queda `confirmed`; su consulta/resolución explícita no suspende el vencimiento más reciente.

Cada versión se publica con `obligation.version.created.v1`; cambios de vencimiento, pago, descarte o entrada en conflicto emiten `obligation.reminder.reschedule.requested.v1` en la misma transacción. V07 sólo programa una versión canónica `confirmed` si la política automática está habilitada; cancela avisos obsoletos y verifica estado y `current_version_id` antes de llamar a Telegram. La transición `candidate`→`confirmed` programa mediante el evento de versión; `paid`/`discarded` no resucitan por replay.
